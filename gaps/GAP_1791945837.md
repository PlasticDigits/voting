# Voting codebase gap analysis

**Review date:** 2026-10-14 UTC

**Report epoch:** `1791945837` (Unix seconds)

**Reviewed commit:** `f8dbe93df953a78b17cb3304b717dcf84c4cd517`

**Scope:** both Rust workspace crates, the frontend package and dependency graph, migrations, deployment files, CI, tests, documentation, and the requested scheduled/collaborative drafting experience. This is an analysis, not a feature implementation.

## Assessment

The repository has a useful foundation: dual-chain registrations, separate ledger/API roles, signed actions, structured drafts, community comments, committee opening, frozen weights, and a Legal-gated dApp. However, important correctness gaps can produce inaccurate balances or open a different revision from the one reviewed. Passing tests currently miss these conditions. Browser amendments also fail cross-origin because the API's CORS policy omits `PUT`.

The additional drafting request is **partly implemented**. Authors can edit published drafts and receive comments; editing stops once voting opens. Future start dates, automatic opening, a start-mode toggle, and additional editors are absent. Immediate author-controlled opening would change the existing committee approval policy, so that part needs an explicit product decision before implementation.

**Priorities:** P0 = blocker for trustworthy public voting; P1 = high-priority defect, security hardening, or explicitly requested feature; P2 = important usability, assurance, maintainability, or operational improvement; P3 = optional enhancement. These are delivery priorities, not CVSS scores. **Evidence:** reproduced = observed in a local probe; inspected = demonstrated by source/control flow; proposed = feature or policy opportunity rather than a current invariant violation.

Recommended order: repair ledger correctness and atomic approval; repair browser amendments and signature validation; strengthen security and regression tests; implement scheduled drafts and collaboration; then improve results, usability, performance, and operations.

## Correctness and release blockers

### GAP-001 — P0: Terra LCD adapter reads transaction bodies instead of execution responses

**Evidence: reproduced.** [ledger/src/lcd.rs](../ledger/src/lcd.rs), `block_txs` and `LcdTx`; [ingest](../ledger/src/ingest.rs), `ingest_terra_height`.

`Search` deserializes `txs` into `LcdTx { txhash, logs, events }`. The standard Cosmos transaction-search response puts decoded transaction bodies in `txs` and hashes/execution events in **`tx_responses`**. Because the expected fields are optional, transaction bodies deserialize successfully with no hash or events. Ingest can advance its cursor while indexing zero transfers. A local standard-response fixture produced `rows=1, hash="", events=0`, despite an execution response containing `REAL_HASH` and a wasm event. This matches the [Cosmos SDK response schema](https://raw.githubusercontent.com/cosmos/cosmos-sdk/v0.50.13/proto/cosmos/tx/v1beta1/service.proto).

**Impact:** registered Terra balances can remain stale after transfers, affecting draft eligibility and frozen voting weights.

**Action:** consume validated `tx_responses`, require execution identity/status, reject malformed responses, and distinguish legitimate empty blocks from adapter/schema failure. Preserve transaction/event order and ignore failed execution where applicable. Add recorded response fixtures from the supported Terra LCD version plus a mock-HTTP-to-Postgres ingest test. Do not advance the cursor on a malformed/incomplete response.

### GAP-002 — P0: duplicate transfer inserts still apply balance deltas

**Evidence: reproduced.** [ledger/src/db.rs](../ledger/src/db.rs), `persist_terra_leg` (172–197) and `persist_bsc_leg` (217–240).

Both paths use `INSERT … ON CONFLICT … DO NOTHING`, then unconditionally read the previous balance and apply the transfer. The affected-row result is ignored. On both chains, a local registered balance of 100 became **90 after the first debit and 80 after replaying the same transfer**, while the transfer row remained unique.

**Impact:** a restart between transfer commit and cursor update, a partial Terra-block retry, or overlapping writer/range processing corrupts the running balance. This undermines the apparent idempotence supplied by unique transfer keys.

**Action:** apply deltas only for newly inserted events, within the same transaction as the corresponding checkpoint/cursor update. Use stable source event identities rather than a registration-filtered event position on Terra. Test duplicate batches, overlapping BSC ranges, retries after partial block processing, multiple events at one height, and injected failures before cursor commit.

### GAP-003 — P0: catch-up applies already-snapshotted transfers to new registrations

**Evidence: reproduced.** [ledger/src/register.rs](../ledger/src/register.rs), [ledger/src/bsc.rs](../ledger/src/bsc.rs), and [ledger/src/db.rs](../ledger/src/db.rs), `is_registered_in_tx`, `tip_balance_in_tx`, checkpoint writes.

Persistence checks only whether a wallet is active, not whether a transfer occurs **after its registration balance boundary**. The latest initial balance is used even when ingest is processing an earlier block. A probe registered a wallet with 50 at block 110, then ingested an incoming 10 at block 109; the balance queried at 110 became **60**, although that transfer was already reflected in the live snapshot. Transfers in the registration block have the same end-of-block double-counting risk.

The initial snapshot is also a separate `latest_height`/`eth_blockNumber` call followed by an unpinned live balance read. The returned balance can belong to a later block or a different failover endpoint, so the stored height and balance need not describe the same state.

**Action:** define a coherent live snapshot boundary per chain; derive/read the balance and its observed block together where supported without requiring an archive node. Apply deltas only after that wallet's boundary, under serialization with registration insertion. If a coherent boundary cannot be obtained, retry instead of accepting an ambiguous snapshot. Test before/at/after registration, chain-tip movement between calls, registration while a range is being fetched, and concurrent register/ingest on both chains.

### GAP-004 — P0: stale-cursor recovery silently loses registered-wallet history

**Evidence: inspected; currently documented behavior.** [ledger/src/ingest.rs](../ledger/src/ingest.rs), `ingest_window`, `INGEST_STALE_GAP`; [L1](../docs/LEDGER_INVARIANTS.md).

A nonzero cursor more than 10,000 blocks/heights behind jumps directly to tip. Existing checkpoints remain, and skipped transfers are never applied or reconciled. A registered holder can transfer out during an outage and retain stale vote power after the jump. The new cursor then appears current even though the ledger is incomplete.

**Action:** distinguish initial boot with no electorate from loss of continuity for existing registrations. Record a durable gap/degraded state and prevent opening a poll using unreliable weights. For recovery, design a new live-balance baseline/epoch and explicit eligibility boundary while preserving existing frozen proposals; do not quietly overwrite historical balances or require an archive node. Tests should model an outage, transfers inside the skipped interval, recovery, and refusal to freeze until accounting continuity is restored. This requires revisiting the documented jump policy, not merely changing a loop constant.

### GAP-005 — P0: amendment and opening approval checks are outside the mutation transaction

**Evidence: inspected, with missing DB enforcement reproduced.** [operator-voting/src/api.rs](../operator-voting/src/api.rs), `amend_sections`, `open_vote`, `attach_analysis`; [DB](../operator-voting/src/db.rs), `update_draft_sections`, `open_proposal`, `insert_analysis`.

The API reads and validates `prev_body_hash`, but `UPDATE` only predicates on `id` and `status='draft'`. Two requests can validate the same old hash and both succeed, overwriting one another. A DB probe accepted two updates with no expected revision. A title-only amendment does not change the body hash, making a body hash insufficient as a complete proposal revision even with an added predicate.

Similarly, the committee validates the current hash before calling `open_proposal`; the transaction does not recheck that hash. An amendment committed between validation and opening can cause the poll to freeze content the committee never approved. Analysis insertion checks draft status only in the API, so it can race opening and append after the freeze. Analysis is not bound to a proposal revision, so old analysis can appear to review an amended draft.

**Action:** use a monotonically increasing proposal revision covering title, sections, and future schedule/editor changes. Validate authorization, expected revision/hash, state, analysis attachment, and signature consumption inside the mutation transaction. Opening must atomically verify the approved revision and freeze the electorate. Add barrier-controlled concurrent amend/amend, amend/open, analyze/open, and duplicate-open tests. Preserve the existing one-time freeze transaction, which is already a good foundation.

### GAP-006 — P1: cross-origin author amendments fail browser CORS

**Evidence: reproduced policy output.** [operator-voting/src/main.rs](../operator-voting/src/main.rs):31–42; [frontend API service](../frontend/src/services/operatorVoting.ts), `amendProposal`.

The frontend uses `PUT /v1/proposals/:id/sections`. Both CORS branches allow only `GET, POST, OPTIONS`. A local `PUT` preflight returned `Access-Control-Allow-Methods: GET,POST,OPTIONS`; a browser on the separate voting origin will refuse the amendment. Router-only API tests and intercepted Playwright requests do not exercise the production middleware.

**Action:** permit `PUT`, validate configured origins instead of silently discarding invalid entries, and add preflight tests using the real application middleware. Add a browser amendment flow against an actual local API on a second origin.

### GAP-007 — P1: timestamp subtraction can panic or bypass the signature TTL

**Evidence: debug panic reproduced; release effect follows Rust wrapping arithmetic.** [operator-voting/src/payload.rs](../operator-voting/src/payload.rs):92.

`expires_at - issued_at` uses unchecked `i64` subtraction. A payload with `issued_at=i64::MIN` and `expires_at=i64::MAX` passes the preceding comparisons and panics in debug. Under ordinary release overflow settings, that subtraction wraps to **-1**, passing the maximum-TTL test and allowing a practically non-expiring signed payload. Validation runs before signature verification, so malformed inputs also reach this arithmetic without a valid signature.

**Action:** require ordered timestamps, a bounded issue-time window, and a positive checked TTL; use `checked_sub` or validated time types. Inject a clock for deterministic expiry tests. Test integer extrema, reversed windows, boundary expiry, clock skew, and release-equivalent arithmetic behavior.

## Security and trust boundaries

### GAP-014 — P1: client HTML sanitizer can leave active descendants untouched

**Evidence: reproduced.** [frontend/src/utils/sanitizeProposalHtml.ts](../frontend/src/utils/sanitizeProposalHtml.ts), the branch that unwraps a disallowed element and immediately `continue`s.

The sanitizer moves a disallowed wrapper's children into its parent without sanitizing or revisiting those children. In jsdom, this input:

```html
<div><img src=x onerror="alert(1)"><a href="javascript:alert(2)">bad</a></div>
```

produced:

```html
<img src="x" onerror="alert(1)"><a href="javascript:alert(2)">bad</a>
```

The no-DOM fallback is also a partial regex filter. Structured proposal sections, comments, and analysis are rendered directly with `dangerouslySetInnerHTML` in [section views](../frontend/src/components/proposal/ProposalSectionFields.tsx) and [detail](../frontend/src/pages/VoteDetailPage.tsx), without the legacy-body sanitization step.

**Risk qualification:** the server's ammonia sanitization protects ordinary current writes; this probe does **not** demonstrate stored XSS through a valid current create request. It demonstrates that the claimed client defense fails for malicious legacy/imported content or an untrusted API response. CSP offers another layer but does not make the sanitizer correct.

**Action:** use a maintained sanitizer at display boundaries, centralize safe-HTML rendering, and retain authoritative server sanitization. Add nested wrapper, SVG/MathML, invalid markup, event attribute, URL-scheme, and sanitizer-parity cases. Keep render sanitation and signed canonicalization contracts explicitly separated so a sanitizer change does not silently break signatures.

### GAP-015 — P1: SECURITY DEFINER balance functions have no pinned search path

**Evidence: reproduced with the restricted role.** [ledger migration 1](../ledger/migrations/20260825000001_ledger.sql), [qualification migration](../ledger/migrations/20260825000003_qualify_balance_fns.sql), [grants](../deploy/grants.sql).

The function bodies reference unqualified tables and do not set a secure `search_path`. Qualifying the **function call** as `public.voting_cl8y_balance_at` does not qualify table lookups inside it. In a fresh restricted-role session, creating temporary tables named `voting_registrations` and `cl8y_balances`, then inserting a fake registered balance, caused the public function to return **999 for a wallet absent from the actual ledger**. The role could create those temporary tables under the local database's default TEMP privilege. This proves table shadowing, not a demonstrated arbitrary-code or persistent ledger-write escalation.

**Action:** schema-qualify all internal relations and set a trusted path with `pg_temp` explicitly last; audit definer ownership and execution grants. Add hostile `search_path`/temporary-table tests. PostgreSQL explicitly documents this requirement for [secure SECURITY DEFINER functions](https://www.postgresql.org/docs/16/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY).

**Policy decision to record before implementation:** does the user request intentionally replace committee-controlled opening, or should the default mean **“open as soon as approved”** and the custom date mean **“open at/after this date once approved”**? Governance doctrine currently requires a feasibility reviewer to control opening. A date alone must not silently become permission to bypass that control. If literal immediate author opening is selected, update the doctrine, API, tests and product copy explicitly.

**Recommended implementation under the current policy:**

1. Preserve an editable `draft`, add signed start intent (`as_soon_as_approved` / `scheduled`) and UTC `scheduled_start_at`, and return both requested and actual opening times. Display local timezone plus UTC, with a real switch label and an accessible date/time field. An immediate default must say what approval is still needed.
2. Introduce explicit approval of a complete proposal revision. Because action signatures currently expire in ten minutes, persist committee approval when signed; do not queue the existing short-lived `open_vote` request for execution weeks later. Treat approved scheduled execution as a separately specified durable authorization.
3. Any relevant edit increments the revision and invalidates approval. Decide whether approval temporarily locks editing or editors may continue editing and trigger reapproval; the request suggests continuing to amend until voting starts. Show this consequence clearly.
4. A durable DB-backed scheduler claims due proposals across replicas, revalidates approval/roles/blacklist/state, checks both chain ledgers, then atomically opens and freezes once. Use database/server time, not browser timers. Retry safely after restarts or crashes without opening twice.
5. Define late-worker and outage behavior. The product must disclose whether the snapshot is taken at **actual opening** or an advertised scheduled instant. Under this repo's freeze-at-open/no-archive design, freeze at actual opening and show delays; do not backdate a later freeze to the requested time. Clarify whether editing closes at the due time or actual start when the worker is delayed.
6. Add signed reschedule/cancel actions, limits on future scheduling, notification/reminder hooks, and clear states such as awaiting approval, scheduled, delayed, open. All mutation controls remain behind Legal; author identity remains per chain/address.

**Acceptance tests:** default mode and custom mode; invalid/past dates; timezone/DST conversion; registered-only feedback; author edit before start; revision change invalidates approval; due-time edit/open race; opening refuses stale BSC/Terra; two scheduler workers; restart after claim/after freeze; duplicate delivery; reschedule/cancel; delayed opening copy; edit rejection through API after actual start; identical behavior for Terra and BSC authors.

### GAP-026 — P1: multiple editors need explicit, bounded permissions

**Evidence: proposed requested feature.** Single proposer field and proposer equality check in [API](../operator-voting/src/api.rs); no editor-membership relation in [migrations](../ledger/migrations/20260830000002_draft_lifecycle.sql).

## Governance expectations that need explicit decisions

### GAP-045 — P2/P3: results interpretation, privacy, roll hygiene and accountability

**Evidence: proposed future features; current public behavior is inspected.** [governance doctrine](../docs/GOVERNANCE_RESEARCH.md), [API](../operator-voting/src/api.rs), [tally/query](../operator-voting/src/db.rs).

## Performance, gas, DRY, readability, and language/library practice

### GAP-046 — P2: unbounded reads and per-proposal/per-event query multiplication

**Evidence: inspected.** [API list](../operator-voting/src/api.rs), [operator DB](../operator-voting/src/db.rs), [ledger DB](../ledger/src/db.rs), [CW20/BEP-20 parsers](../ledger/src/parser).

### GAP-048 — P2: protocol duplication needs shared contracts rather than parallel implementations

**Evidence: inspected.** [Rust sections](../operator-voting/src/proposal_sections.rs), [TypeScript sections](../frontend/src/utils/proposalSections.ts), [Rust payload](../operator-voting/src/payload.rs), [TS payload](../frontend/src/utils/votingPayload.ts), [frontend API types](../frontend/src/services/operatorVoting.ts), and [Legal vendor mocks](../frontend/src/vendor).

**Evidence: inspected.** API is ~815 lines, DB ~520, detail page ~425, and ported Terra wallet service ~530. ### GAP-050 — P2/P3: gas optimization is not applicable to voting; remove misleading leftovers

Registration, draft edits, comments, opening and voting use offchain signatures and HTTP calls. `eth_call`/LCD reads do not make a holder pay transaction gas. There are no contracts to optimize and no reason to introduce one for this request. The relevant cost optimizations are RPC requests, DB operations, application latency and wallet signing prompts (GAP-046/047).

Do not propose gas-price reductions as a fix for registration/signing latency.
